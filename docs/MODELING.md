# Контракт эксперимента и подготовка признаков

Перед обучением нужен явный JSON-контракт: тип задачи, целевой столбец и его предметный смысл, числовые и категориальные признаки, группирующий идентификатор, исключаемые поля и seed. `check-spec` проверяет структуру контракта и колонок. Формальная проверка не доказывает, что показатель правильно оценивает эффективность сотрудника.

Пример структуры, названия необходимо заменить полями утверждённого реального набора:

```json
{
  "task": "regression",
  "target": "approved_target",
  "target_description": "Определение показателя, периода и способа измерения",
  "numeric_features": ["approved_numeric_feature"],
  "categorical_features": ["approved_category"],
  "group_column": "employee_id",
  "excluded_columns": ["post_outcome_total"],
  "seed": 42
}
```

Числовые пропуски заполняются медианой train; затем используется StandardScaler. Для категорий используются отдельное значение пропуска и one-hot с обработкой неизвестных значений без изменения обученного словаря. Полностью пустой на train числовой столбец сохраняет размерность с нулевой подстановкой. Набор признаков задан явно, поэтому порядок или наличие других колонок не влияют на состав входов.

Преобразования обучаются только на train; validation и test используют transform. Новые данные для применения могут не содержать целевой столбец. Поля цели, группового идентификатора и исключаемых столбцов запрещены среди признаков. Производные цели также нужно выявлять предметным анализом: код не способен автоматически распознать все такие зависимости.

Методическая основа: [scikit-learn — утечка данных и Pipeline](https://scikit-learn.org/stable/common_pitfalls.html), [OneHotEncoder](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.OneHotEncoder).

Фикстуры проверок служат исключительно тестированию программного конвейера и не являются данными или результатами дипломного исследования.

## Базовые модели

Для классификации сравниваются прогноз наиболее частого класса train и логистическая регрессия с балансировкой весов классов. Для регрессии сравниваются среднее целевого показателя train и Ridge с коэффициентом регуляризации 1. Масштабирование, подстановка пропусков и кодирование категорий входят в сохраняемый Pipeline каждой модели.

Линейный регрессионный baseline минимизирует сумму квадратов ошибок с добавкой alpha × суммы квадратов весов. Константный baseline помогает проверить, даёт ли использование признаков преимущество перед простым прогнозом.

Метрики классификации: Accuracy — доля верных прогнозов; macro-F1 — среднее F1 по классам с одинаковым весом класса. Метрики регрессии: MAE — средняя абсолютная ошибка; RMSE — корень из средней квадратичной ошибки; R² — доля объяснённой вариации. Для константного целевого показателя или слишком короткой выборки R² сохраняется как null.

Модель выбирается по macro-F1 validation (классификация) либо MAE validation (регрессия). Test не используется для обучения преобразований, весов или выбора baseline. Показатели train/validation/test сохраняются раздельно. Изменение меток heldout в тесте программы не меняет обученные параметры моделей.

Команда `train-baseline` принимает готовые выборки и JSON-контракт. До обучения проверяются контрольные суммы, размеры, структура, отсутствие пересечения групп и минимальный общий объём 1000 строк / 10 колонок. Сохраняются model1.joblib, model2.joblib, config.json, metrics.json. Конфигурация и отчёт указывают выбранную модель и точные версии библиотек; существующий каталог результата не перезаписывается.

Эта реализация готовит воспроизводимый эксперимент, но выбор предметной цели и данных пока не утверждён. DL, подбор гиперпараметров, анализ ошибок и интерфейс остаются следующими этапами.
