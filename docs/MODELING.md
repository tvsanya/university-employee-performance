# Контракт эксперимента и подготовка признаков

Перед обучением нужен явный JSON-контракт: тип задачи, целевой столбец и его предметный смысл, числовые и категориальные признаки, группирующий идентификатор, исключаемые поля и seed. `check-spec` проверяет структуру контракта и колонок. Формальная проверка не доказывает, что показатель правильно оценивает эффективность сотрудника.

Пример структуры, названия необходимо заменить полями утверждённого реального набора:

```json
{
  "task": "regression",
  "target": "approved_target",
  "target_description": "Определение показателя, периода и способа измерения",
  "numeric_features": ["approved_numeric_feature"],
  "categorical_features": ["approved_category"],
  "group_column": "employee_id",
  "excluded_columns": ["post_outcome_total"],
  "seed": 42
}
```

Числовые пропуски заполняются медианой train; затем используется StandardScaler. Для категорий используются отдельное значение пропуска и one-hot с обработкой неизвестных значений без изменения обученного словаря. Полностью пустой на train числовой столбец сохраняет размерность с нулевой подстановкой. Набор признаков задан явно, поэтому порядок или наличие других колонок не влияют на состав входов.

Преобразования обучаются только на train; validation и test используют transform. Новые данные для применения могут не содержать целевой столбец. Поля цели, группового идентификатора и исключаемых столбцов запрещены среди признаков. Производные цели также нужно выявлять предметным анализом: код не способен автоматически распознать все такие зависимости.

Методическая основа: [scikit-learn — утечка данных и Pipeline](https://scikit-learn.org/stable/common_pitfalls.html), [OneHotEncoder](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.OneHotEncoder).

Фикстуры проверок служат исключительно тестированию программного конвейера и не являются данными или результатами дипломного исследования.

## Базовые модели

Для классификации сравниваются прогноз наиболее частого класса train и логистическая регрессия с балансировкой весов классов. Для регрессии сравниваются среднее целевого показателя train и Ridge с коэффициентом регуляризации 1. Масштабирование, подстановка пропусков и кодирование категорий входят в сохраняемый Pipeline каждой модели.

Линейный регрессионный baseline минимизирует сумму квадратов ошибок с добавкой alpha × суммы квадратов весов. Константный baseline помогает проверить, даёт ли использование признаков преимущество перед простым прогнозом.

Метрики классификации: Accuracy — доля верных прогнозов; macro-F1 — среднее F1 по классам с одинаковым весом класса. Метрики регрессии: MAE — средняя абсолютная ошибка; RMSE — корень из средней квадратичной ошибки; R² — доля объяснённой вариации. Для константного целевого показателя или слишком короткой выборки R² сохраняется как null.

Модель выбирается по macro-F1 validation (классификация) либо MAE validation (регрессия). Test не используется для обучения преобразований, весов или выбора baseline. Показатели train/validation/test сохраняются раздельно. Изменение меток heldout в тесте программы не меняет обученные параметры моделей.

Команда `train-baseline` принимает готовые выборки и JSON-контракт. До обучения проверяются контрольные суммы, размеры, структура, отсутствие пересечения групп и минимальный общий объём 1000 строк / 10 колонок. Сохраняются model1.joblib, model2.joblib, config.json, metrics.json. Конфигурация и отчёт указывают выбранную модель и точные версии библиотек; существующий каталог результата не перезаписывается.

Для разработки пользователь выбрал явную симуляцию. Дальнейшие разделы описывают DL и подбор параметров на ней; анализ ошибок, графики и интерфейс развиваются следующими этапами.

## Глубокая табличная сеть

Реализована полносвязная MLP для классификации с двумя–четырьмя скрытыми слоями. Для небольшого набора табличных признаков это проверяемая компактная архитектура без предположения о пространственном или временном порядке. Базовый вариант: вход → Dense(32, ReLU) → Dense(16, ReLU) → выход по классам. Для трёх классов применяется softmax; для двух — один логистический выход. Число входов, выходов и обучаемых параметров сохраняется по фактической модели.

Каждый скрытый слой вычисляет h = activation(W × x + b); выход преобразует значения в вероятности. Adam обучает веса по кросс-энтропии с L2-регуляризацией. Опциональные сбалансированные веса классов вычисляются только по train. Подстановка пропусков, масштаб и словарь категорий также обучаются исключительно на train.

Одна эпоха выполняется через partial_fit. Встроенное случайное early_stopping отключено: внешняя validation уже разделена по сотрудникам. После каждой эпохи сохраняются train loss и train/validation Accuracy и macro-F1. Лучший checkpoint выбирается по максимальному validation macro-F1, первая эпоха выигрывает при равенстве. Patience отсчитывает эпохи без улучшения больше min_delta. Test вообще не передаётся в функцию обучения. Сохраняется именно лучший checkpoint, а не последнее состояние.

Реализация использует [официальный MLPClassifier](https://scikit-learn.org/stable/modules/generated/sklearn.neural_network.MLPClassifier.html). Регрессионный DL в текущей итерации не поддерживается и возвращает явную ошибку; регрессионные baseline остаются доступны.

## Поиск конфигурации на симуляции

`train-neural` принимает готовые групповые выборки, контракт и сетку из 1–8 различных конфигураций. Каждый вариант обучается на train и выбирает эпоху по validation; между вариантами сравнивается validation macro-F1, при равенстве предпочтительна меньшая сеть. Test оценивается только после выбора варианта и checkpoint. Сохраняются model3.joblib, config.json, grid.json, полная история training.json, метрики и контрольные суммы.

Первый демонстрационный поиск: 3000 синтетических строк, 2100/450/450 по независимым сотрудникам. Из трёх вариантов выбран 16 → 32 → 16 → 3 (1123 параметра), checkpoint эпохи 17. Validation macro-F1 сети 0.79580, test 0.77140; Accuracy test 0.78444. Линейная baseline имеет validation macro-F1 0.79764 и test 0.74705. По заранее выбранному validation-критерию линейная модель пока слегка предпочтительнее сети; более высокий test сети не используется для смены правила выбора. Все эти числа относятся только к симуляции.

## Применение сохранённой сети

`predict` читает model.json, а не joblib: числовые параметры преобразований, словари категорий, матрицы весов, смещения, классы и активации. JSON не десериализует Python-объекты. Перед применением проверяются формат, размер файла, размеры слоёв, конечность чисел, положительные масштабы и соответствие назначения происхождению. Неизвестные категории дают нулевой one-hot, пропуски обрабатываются сохранёнными train-статистиками.

Команда сохраняет новый каталог с predictions.csv (исходный номер строки, доступный ID, класс и вероятности) и report.json (контрольные суммы, происхождение модели и входа, назначение и словарь колонок вероятностей). Целевая колонка не нужна, обучение не запускается. JSON-предсказания на всех 450 тестовых строках совпали с исходным Pipeline в пределах 1e-12; повторное обучение также воспроизвело побайтово идентичный joblib-checkpoint. Синтетическая модель сохраняет development_demo_only даже при применении к немаркированному CSV.
